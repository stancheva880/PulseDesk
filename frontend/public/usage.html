Documentation

How to use PulseDesk

A complete walk-through of every role, every screen and every scenario in the app — from the first super-admin login to recording a customer's payment.

Audience: super admins, club admins, trainers, and customers
Scope: Phases 1 – 4
Reading time: ~15 minutes

DEV Running locally

PulseDesk is an npm-workspaces monorepo. The repo root has a top-level package.json that fans out scripts to backend/ and frontend/. Run everything from the repo root unless noted.

Prerequisites

  • Node.js ≥ 24 (the repo pins this in .nvmrc). Use nvm or fnm to switch.
  • npm 10+ (ships with Node 24).
  • No external DB needed for dev — Prisma uses a local SQLite file.

Install & configure

  1. Clone & install 
    git clone <repo-url> pulsedesk
cd pulsedesk
npm install
    The single root npm install hydrates both workspaces.
  2. Set up environment files Each workspace has its own env file: 
    cp backend/.env.example backend/.env
# the frontend has no example file — create frontend/.env.local with:
#   NEXT_PUBLIC_API_URL=http://localhost:4000
#   NEXT_PUBLIC_DEFAULT_LOCALE=bg
    Backend reads: DATABASE_URL, JWT_ACCESS_SECRET (access tokens are signed JWTs; refresh tokens are opaque random + SHA-256, so there is no refresh secret), JWT_ACCESS_TTL, JWT_REFRESH_TTL, CORS_ALLOWED_ORIGINS, FRONTEND_URL, MAIL_TRANSPORT (console or smtp) + SMTP_*, INVITE_TTL_HOURS, PASSWORD_RESET_TTL_HOURS, SUPERADMIN_EMAIL / SUPERADMIN_PASSWORD (used only by the seed), PORT (default 4000).
    Frontend reads: NEXT_PUBLIC_API_URL, NEXT_PUBLIC_DEFAULT_LOCALE.
  3. Initialize the database & seed 
    npm --workspace backend exec -- prisma migrate dev
npm run seed
    The first command applies the schema; the second seeds the two languages (bg default, en), the super-admin user (from your env vars), a demo tenant, and demo Admin + Teacher accounts.
What does the seed create? Two languages (bg default, en), a super-admin account from SUPERADMIN_EMAIL / SUPERADMIN_PASSWORD, a demo tenant (demo-sports-club), and a demo ADMIN + EMPLOYEE account (local-dev passwords — see prisma/seed.ts). Locations, classes and trainees are not seeded — you create those yourself.

Start the app

Both servers together (recommended)

npm run dev

Starts backend on http://localhost:4000 (Nest with --watch) and frontend on http://localhost:3000 (Next dev server) in parallel via workspace fan-out.

Just the backend

npm run dev --workspace backend

API only, on :4000. Useful when you're hacking on Postman / curl flows.

Just the frontend

npm --workspace frontend run dev

UI only, on :3000. Useful when you already have a backend running elsewhere.

Port already in use? A previous run may still be alive. Find it with lsof -i :4000 (macOS/Linux) or netstat -ano | findstr :4000 (Windows) and kill it before re-starting.

Tests

TDD is mandatory in this codebase — write the failing spec first, then the implementation. Vitest is used in both workspaces.

All tests, both workspaces

npm run test

Single workspace

npm run test --workspace backend
npm run test --workspace frontend

One file or one test by name

# by file path
npm --workspace backend exec -- vitest run src/auth/auth.service.spec.ts

# by test name (regex against describe + it)
npm --workspace backend exec -- vitest run -t "validateUser"

# frontend example
npm --workspace frontend exec -- vitest run __tests__/home.test.tsx

Watch mode

npm --workspace backend exec -- vitest         # interactive watcher
npm --workspace frontend exec -- vitest        # same on the frontend

Goal Command Notes
Production build (both) npm run build Nest tsc + Next production build
Build only backend npm run build --workspace backend Outputs to backend/dist
Build only frontend npm run build --workspace frontend Outputs to frontend/.next

Prisma & database

All Prisma commands run from the backend workspace.

# create a new migration after editing schema.prisma
npm --workspace backend exec -- prisma migrate dev --name <name>

# regenerate the typed client (run after schema edits if you didn't migrate)
npm --workspace backend exec -- prisma generate

# open the visual data browser
npm --workspace backend exec -- prisma studio

# re-seed (drops nothing — adds the demo tenant + super-admin)
npm run seed
Schema portability. The Prisma schema is written to be portable to Postgres / MySQL — cuid IDs, no @db.* annotations, Prisma enums. Keep new models in that style; don't introduce SQLite-only syntax.

End-to-end smoke test

Once npm run dev is up:

  1. Open http://localhost:3000.
  2. Sign in with the seed super-admin (SUPERADMIN_EMAIL + SUPERADMIN_PASSWORD from backend/.env).
  3. Pick the demo tenant from the navbar selector.
  4. Create a Location → a Class → a Schedule → generate Sessions → mark Attendance.

DOCKER Running with Docker

The whole stack runs in containers — either optimized production images, or development with hot reload on both backend (nest start --watch) and frontend (next dev). The Docker build context is the repo root because the single npm-workspaces lockfile lives there.

Prerequisites

  • Docker Desktop running, with Compose v2 (the docker compose subcommand).
  • One-time setup — create the env file (gitignored): 
    cp .env.docker.example .env.docker
    Then set at least JWT_ACCESS_SECRET (openssl rand -base64 32) and SUPERADMIN_PASSWORD. The defaults boot fine for local dev but are not safe to deploy.

Development (hot reload) — the default

docker compose up --build

This merges docker-compose.yml + docker-compose.override.yml automatically:

  • Frontend → http://localhost:3000, backend → http://localhost:4000/api.
  • Your working tree is bind-mounted; edits on the host reload the running containers. File watching uses polling (CHOKIDAR_USEPOLLING / WATCHPACK_POLLING), which is required on Windows / Docker Desktop.
  • On boot the backend applies migrations and seeds the super-admin (RUN_SEED=true).

Stop with docker compose down — your data persists in the pulsedesk-db volume.

Production

docker compose -f docker-compose.yml up --build

Builds optimized images (backend → compiled dist; frontend → Next.js standalone server) and runs them. Migrations and the idempotent seed run on the backend's first boot.

The API URL is baked at build time. NEXT_PUBLIC_API_URL is inlined into the browser bundle during next build. The default http://localhost:4000 is correct for a single host; to bake a different host, set it in your shell before building: 
NEXT_PUBLIC_API_URL=https://api.example.com docker compose -f docker-compose.yml build

Common operations

# tail logs
docker compose logs -f backend

# migration status / create a new migration (dev)
docker compose exec backend sh -c "cd /app/backend && npx prisma migrate status"
docker compose exec backend sh -c "cd /app/backend && npx prisma migrate dev --name <name>"

# re-run the idempotent seed
docker compose exec backend sh -c "cd /app/backend && npx prisma db seed"

# wipe the database volume (destructive)
docker compose down -v
Where's the database? SQLite lives on the named pulsedesk-db volume at /data/pulsedesk.db — outside the source tree and the bind mount, so it survives rebuilds and avoids Windows bind-mount file locking. Boot behaviour is controlled by RUN_MIGRATIONS / RUN_SEED in .env.docker.
Files involved. backend/Dockerfile, frontend/Dockerfile, docker-compose.yml (production base), docker-compose.override.yml (dev overlay), .dockerignore, and .env.docker.example. See DOCKER.md for the full reference.

01 What is PulseDesk?

PulseDesk is a multi-tenant SaaS for sports clubs and trainers. Each tenant (a club, a studio, a private trainer) gets a fully isolated workspace where they manage locations, classes, schedules, trainees, attendance, and fees.

For owners

Set up locations, classes, pricing and recurring schedules; generate concrete sessions for the week or month.

For trainers

See the sessions you teach, mark each trainee present / absent / excused, and leave notes.

For customers

See your upcoming sessions, RSVP, and review the fees and payments for you or your dependents.

02 Tenants

A tenant is the isolation boundary of the application. Every record — locations, users, trainees, fees — belongs to exactly one tenant, and tenants never see each other's data.

How tenants are identified

  • Each tenant has a unique slug (e.g. demo-sports-club) and a human-friendly name.
  • Everyone — admins, employees, customers, and super admins — logs in with just their email + password. Email is globally unique, so it resolves to exactly one account; the slug is not entered at login.
  • The slug is an internal identifier (used in URLs and by super admins when switching tenants), not something members type to sign in.

Where tenant context comes from

For tenant users, the tenant is permanently attached to their account at sign-up — they cannot act outside it. The backend reads the tenant from the JWT, never from a header, so it cannot be spoofed.

SUPER_ADMIN is different. A super admin's account has no tenant. To act inside a tenant (create a class, view fees, etc.), the super admin selects a tenant from the in-app tenant selector; the UI then sends an X-Tenant-Id header with every request.

TL;DR. Tenant users are tied to one tenant for life. Super admins are global and "shop into" a tenant when they need to operate inside it.

03 Roles overview

PulseDesk has four roles. Each role determines what a user can do and where they can do it.

SUPER_ADMIN

Platform owner

Cross-tenant. No location restriction. Full power.

  • Sees and manages every tenant
  • Creates / edits / deletes Locations
  • Creates other super admins, admins, employees, customers
  • Cannot delete themselves (lockout protection)
  • Has access to the tenant selector in the navbar
ADMIN

Club / studio admin

Scoped to assigned Locations within their tenant.

  • Manages classes, trainees, schedules, fees at their assigned Locations only
  • Cannot create or edit Locations themselves (super-admin only)
  • Creates employees and customers — never super admins or other admins
  • Cannot delete a super admin under any circumstances
  • Cannot widen their own location set
EMPLOYEE

Trainer / coach

Sees the work assigned to them.

  • Sees only the classes and sessions they teach
  • Marks attendance and leaves session notes on those sessions
  • Read-only everywhere else — no create / edit / delete buttons
  • No access to Schedules or Users
CUSTOMER

Trainee / parent

Self-service portal only.

  • Sees upcoming sessions for themselves and their dependents
  • Sends RSVPs (Confirmed / Decline / Reschedule)
  • Reviews their own fees and payment history
  • Has no access to the admin dashboard or to other customers' data
What a trainer (EMPLOYEE) sees in the dashboard. The interface is tailored to the role, so trainers aren't shown actions they can't perform:
  • The sidebar hides Schedules and Users — sections trainers can't open.
  • Classes and Sessions list only the ones they teach, not the whole tenant.
  • Pages they can read — Classes, Sessions, Trainees, Locations, Fees — show no New / Edit / Delete buttons; the view is read-only. The home dashboard hides the revenue chart.
  • The one thing they change is attendance: every session they teach keeps a working Mark attendance screen.
This is also enforced server-side — the UI simply hides what the API would reject.

05 First-time login

The login form has two fields: email and password. Email is globally unique across PulseDesk, so it identifies exactly one account — the same form works for super admins and tenant users alike.

Logging in as a super admin

  1. Open the sign-in page Navigate to /login.
  2. Enter your super-admin email and password These come from the seed (SUPERADMIN_EMAIL / SUPERADMIN_PASSWORD env vars) on first install.
  3. Submit You'll land on the dashboard with the tenant selector visible in the navbar.

Logging in as a tenant user

  1. Enter your email and password These were created when an admin invited you. No tenant slug needed — your account is already tied to its tenant, and that's where you'll land.
  2. Submit You'll see only your tenant's data — locations, classes, trainees, etc. — and only the parts your role allows.
Generic error on failure. A wrong email or password returns the same "Invalid credentials" message — the backend never reveals whether an email is registered, to avoid leaking which accounts exist.

06 Reset a forgotten password

Users who forget their password recover access on their own — no admin intervention. The flow is the standard one: ask for the email, mail a one-time link, set a new password from the link.

From the user's side

  1. Open the login page Click Forgot your password? below the password field.
  2. Enter your email Just the email — no tenant slug. The same email maps to one account, regardless of which tenant you belong to.
  3. Submit You'll always see the same confirmation: "If an account exists for that email, you'll receive instructions shortly." The page deliberately does not reveal whether the email is registered.
  4. Check your inbox The email contains a single-use link. Links expire after 1 hour by default (configurable via PASSWORD_RESET_TTL_HOURS).
  5. Click the link, pick a new password Minimum 8 characters. Confirm it. Submit.
  6. Sign in normally You're sent back to /login with a green success banner. Use your new password to sign in — there is no auto-login from the reset link itself.

What happens behind the scenes

  • The reset link contains a 32-byte random token. The backend stores only its SHA-256 hash, never the raw token.
  • Submitting the form again invalidates any prior unused link — only the most recent link works.
  • On successful reset, every active session for the account is revoked — refresh tokens are nuked, so all browsers, tabs and devices need to log in again with the new password.
  • Inactive (deactivated) accounts are silently skipped — the reset flow is not a back-door for re-activating a deactivated user.
  • Email is globally unique, so a reset request maps to exactly one account — there's no ambiguity about which user to reset.
Dev mode tip. With MAIL_TRANSPORT=console (the default in backend/.env.example), reset emails aren't actually sent — they're printed to the backend log. Look for a block starting with "OUTGOING MAIL" in the dev-server output to grab the reset URL when testing.
No auto-login. Resetting the password does not create a session. You're bounced back to /login with a banner. This contains the blast radius if a reset link is ever intercepted — possession of the link alone doesn't grant access.

07 Switching tenants SUPER_ADMIN only

The tenant selector is a dropdown in the top navbar that only renders when the logged-in user is a super admin.

How it works

  1. Open the dropdown It loads the list of tenants from GET /api/tenants.
  2. Pick a tenant The selection is saved to localStorage under pulsedesk.tenantContext.
  3. The page reloads From that point on, every API request includes an X-Tenant-Id header pointing at the chosen tenant. You're now operating inside that tenant.
  4. Switch back any time Choose a different tenant from the dropdown to reset the context.
Why the header? The JWT alone can't carry tenant context for a super admin (their tenantId is null). The header gives the super admin an explicit, auditable way to declare "I am acting on behalf of tenant X for this request". Tenant users' headers are ignored by the backend, so there is no way to escalate privilege.
Forgot to pick a tenant? Calls that need tenant context will fail with a "X-Tenant-Id header required for SUPER_ADMIN" error. Just open the selector and pick one.

08 Language switcher

PulseDesk ships with English and Bulgarian. The default locale is Bulgarian (bg); you can switch from the navbar. Your choice is persisted in localStorage under pulsedesk.locale and applies to every screen.

All form labels, buttons, and validation errors are translated. Error messages from the backend still come in English; the frontend wraps them in localized callouts where it makes sense.

09 Add a Location

SUPER_ADMIN

Locations are the physical places where classes happen — a gym, a hall, an outdoor pitch. Only super admins create them. Admins read the locations they're assigned to but cannot add, rename, or delete them.

  1. Pick a tenant From the tenant selector. Locations belong to exactly one tenant.
  2. Open Locations Click Locations in the sidebar.
  3. Click "New location" The form opens with two required fields.
  4. Fill in name and address The name must be unique within the tenant. The address is optional but recommended.
  5. Save The new location is now selectable when you create classes, trainees, or schedules in this tenant.

Editing & deleting

From the list page, each location has an Edit and Delete action. Deleting is restricted by referential integrity — if classes, schedules, or trainees still reference the location, the delete is blocked. Reassign or remove the dependents first.

10 Create a Class

SUPER_ADMIN ADMIN (scoped)

A Class is a definition — "Adult yoga, billed monthly at €60". A class is offered at one or more Locations and can be billed either per month or per session.

  1. Open Classes Click Classes in the sidebar.
  2. Click "New class" A form opens.
  3. Enter a name and (optional) description The name must be unique within the tenant.
  4. Choose a billing mode PER_MONTH bills a flat amount per trainee per calendar month. PER_SESSION bills per attended session. Billing mode is immutable — once a class is created you cannot switch modes; create a new class instead.
  5. Set the price Either monthly amount or price per session, depending on the mode.
  6. Pick the Locations You can only pick from the locations you have access to. Admins are limited to their assigned set; super admins see all locations in the active tenant.
  7. Enrol trainees (optional) Tick the members for this class under Trainees — this is the class roster. You can leave it empty now and manage it later from the class's Edit page.
  8. Assign trainers (optional) Tick the staff who teach this class under Trainers. Trainers are EMPLOYEE users — create them under Users first. These become the class's default trainers: every session generated for the class is pre-assigned to them. Leave it empty to assign trainers per session instead.
  9. Save The class is now ready to be scheduled.
Why immutable billing? Past fees were generated under one billing model. Switching the model on the same class would corrupt historical reporting.
Managing the roster. A class's Edit page has the same Trainees checklist — tick or untick to change who's enrolled. Adding a trainee (here or from the trainee's own form) puts them on the class's future scheduled sessions automatically; past and completed sessions are left untouched. Unticking only stops future auto-enrolment — it does not delete attendance already recorded.
Changing trainers later. The Edit page also has the Trainers checklist. Adjusting it changes the defaults for future sessions only — sessions that already exist keep whoever was assigned when they were created. To swap the trainer on an existing session (e.g. a substitute), edit that session directly — see the next section.

11 Build a Schedule & generate Sessions

SUPER_ADMIN ADMIN (scoped)

A Schedule is a recurring weekly slot — "Adult yoga, every Monday 18:00–19:00 at Hall A". A Session is the concrete occurrence on a specific date. Sessions are generated from active schedules in bulk for a date range.

Step 1 — define the schedule

  1. Open Schedules Sidebar → Schedules.
  2. Click "New schedule" Pick the class, the location (must be one the class is offered at), the day of the week, and the start / end time in HH:MM 24-hour format.
  3. Save The schedule is active by default. Inactive schedules will be skipped during generation.

Step 2 — generate sessions for a date range

  1. Click "Generate sessions" Above the schedules list.
  2. Pick a "from" and "to" date The end date must be on or after the start date.
  3. Optional — limit to a single class Useful if you only want to extend one class's sessions.
  4. Submit You get a result line: "Created N session(s); skipped M duplicate(s)". Duplicates are detected via (class, location, startsAt) uniqueness, so re-running the generator on the same range is safe.
Best practice. Generate sessions one month at a time at the start of each month. That keeps the calendar full without flooding the table with sessions you might cancel.
Who teaches a session. Every generated session inherits the class's Trainers automatically. To set or override them for a single occurrence — say a substitute covering one Monday — open that session's Edit page and adjust its Trainers checklist; saving replaces only that session's trainers, leaving the class defaults and every other session untouched. An ad-hoc session created with New session has the same picker — leave it empty to inherit the class's trainers.

12 Add a Trainee (and the under-18 rule)

SUPER_ADMIN ADMIN (scoped)

A Trainee is a member who attends classes. Trainees can be linked to a customer account (so a parent or the trainee themselves can RSVP and view fees from the portal).

  1. Open Trainees Sidebar → Trainees → New trainee.
  2. Fill in name and date of birth The DOB drives the under-18 rule below.
  3. Pick the Locations The trainee will only appear in classes at these locations. Admins can only assign locations they themselves have access to.
  4. Enroll in Classes Tick the classes this trainee should attend. This is how a trainee gets onto a session's attendance — when a session is created for a class, everyone enrolled in that class is given a PENDING attendance row.
  5. Add guardian contacts (if minor) The form shows a "Guardian contacts" section. If the trainee is under 18 you must add at least one contact. The backend rejects the request otherwise.
  6. Save The trainee is now active. Anyone enrolled in a class will appear on that class's future sessions.
Enrollment now updates upcoming sessions automatically. Enrolling a trainee in a class — from the trainee form or the class's Trainees roster — creates attendance rows for that class's future scheduled sessions. Past and completed sessions are left untouched. To add someone to one specific existing session, use Add trainee on that session's attendance page.
Under-18 enforcement. If you set a DOB making the trainee less than 18 years old and submit without contacts, you'll see a 400 error. Add at least one contact (parent, guardian, grandparent, etc.) and try again.

Editing contacts later

From the trainee detail page you can add, edit and remove contacts. You can also flag one contact as the primary — that's the one notifications go to first.

13 Add a User & assign Locations

"Users" means the human accounts that can log into the app. Trainees are not necessarily users — you only create a user when someone needs to sign in (an admin, a trainer, or a parent who wants the portal).

Who can create whom

Creator Can create super admin? Can create admin? Can create employee? Can create customer?
SUPER_ADMIN Yes Yes (with locations) Yes (with locations) Yes (with locations)
ADMIN Forbidden (403) Forbidden (403) Yes — scoped to their locations Yes — scoped to their locations
  1. Open Users Sidebar → Users.
  2. Click "New user" Fill in email, password, and name.
  3. Choose the role The dropdown only offers roles you're allowed to create. An admin will not see SUPER_ADMIN or ADMIN options.
  4. Assign Locations Required for ADMIN, EMPLOYEE, CUSTOMER. The user will only see and act on resources at these locations. SUPER_ADMIN users have no location selector — they see everything.
  5. Save The user can now log in with their email + password.

Editing a user

  • Update name, password, active status, and locations.
  • The role can only be changed by a super admin. Admins editing a user may not change the role field.
  • Self-edit: any user can edit their own profile (name, password) regardless of the location-scope rules — they cannot change their own role.

Deleting a user

  • ADMIN deleting a SUPER_ADMIN → 403 Forbidden.
  • SUPER_ADMIN deleting themselves → 403 Forbidden (lockout protection).
  • Otherwise allowed.

14 Mark Attendance

SUPER_ADMIN ADMIN (scoped) EMPLOYEE (their sessions)

Attendance is captured per (session, trainee). Each row has a status — PENDING, PRESENT, ABSENT or EXCUSED — and the trainee's RSVP (set from the customer portal) is shown alongside.

  1. Open Sessions Sidebar → Sessions.
  2. Click "Mark attendance" on a session You see one row per enrolled trainee.
  3. Add a missing trainee (optional) Use the Add trainee picker at the top to drop in anyone who isn't on the session yet — handy for a one-off guest. It adds a single PENDING row to this session only and does not change the class roster.
  4. Tap the status for each trainee Switch freely between PENDING / PRESENT / ABSENT / EXCUSED.
  5. Click "Save all" All rows are saved in a single transactional bulk request. You'll see "Saved N row(s)".
Empty session? Use the Add trainee control at the top of the attendance page to drop anyone onto this session on the spot. To populate sessions in bulk, enrol trainees via the Classes field on the trainee form or a class's Trainees roster — future scheduled sessions pick them up automatically.

15 Generate Fees

SUPER_ADMIN ADMIN (scoped)

Fees are generated in bulk at the start of a billing period — never typed in by hand for routine months. The generator looks at your active classes and trainees and creates one fee row per (trainee, period).

Monthly fees

  1. Open Fees Sidebar → Fees.
  2. Click "Generate monthly fees" Pick the period start and end (typically a calendar month).
  3. Submit The system creates one fee per trainee per PER_MONTH class for that period. Duplicates are detected via (trainee, class, periodStart, periodEnd), so re-running is safe — it only fills gaps.

Per-session fees

  1. Click "Generate per-session fees" Pick a date range.
  2. Submit The system creates one fee per (trainee, session) for PER_SESSION classes whose sessions fall in the range.

Manual fees

For one-off charges (a private session, a tournament fee), click New fee and enter the trainee, class, amount, period, and optional notes. The amount must be positive and the period end must be ≥ period start.

Fee status

Every fee starts as UNPAID. As payments are recorded, the status auto-updates:

  • Sum of payments == amount → PAID
  • 0 < sum of payments < amount → PARTIAL
  • Sum of payments == 0 → UNPAID

Removing a payment recomputes the status — you don't update it by hand.

16 Record a Payment

SUPER_ADMIN ADMIN (scoped)

Payments are a manual ledger — there is no external payment gateway. You log what you've actually received (cash, bank transfer, etc.) and the fee status updates automatically.

  1. Open the fee detail page From the Fees list, click on a row.
  2. Click "Record a payment" Enter the amount, the date received, the method (cash / transfer / other), and optional notes.
  3. Save The payment appears in the ledger. The fee status recomputes — UNPAID → PARTIAL → PAID as the total catches up.
Removing a payment. Removing a payment row triggers a recompute and may move the fee status backwards (PAID → PARTIAL or UNPAID). The action is logged with the user who did it.

17 Customer Portal

CUSTOMER

Customers see a slim, focused portal — no admin sidebar, no settings. Just two pages: their schedule and their fees.

Schedule

  • Lists upcoming sessions for the customer and any dependent trainees.
  • For each session, the customer can RSVP: Confirmed, Decline, or Reschedule. RSVPs are visible to the trainer in the attendance screen so they know what to expect.
  • The RSVP is independent of attendance — actual presence is still marked by the trainer.

Fees

  • Lists every fee the customer owes or has paid, grouped by trainee.
  • Each fee shows the amount, period, status, and full payment history.
  • Customers cannot record payments themselves — they pay offline; the admin logs the receipt.

18 Data model at a glance

How the pieces hang together. Every arrow is a relationship.

Tenant → Locations → Classes → Schedules → Sessions → Attendance
Tenant → Trainees → Contacts (if < 18)
Tenant → Users ↔ Locations (M2M)
Trainee × Class × Period → Fee → Payments (ledger)
Multi-tenancy invariant. Every row in every tenant-scoped table carries a tenantId column. A user with tenantId = NULL is — by definition — a super admin.

19 Policy quick reference

The rules the backend enforces, distilled into one page. The frontend mirrors them but the backend is the source of truth.

Tenant context

  • Tenant users always operate inside their JWT-bound tenant. Headers cannot widen this.
  • Super admins must send X-Tenant-Id on tenant-scoped requests. Missing or invalid → 400. Header pointing at a non-existent or inactive tenant → 404.

Role bypass

  • SUPER_ADMIN bypasses every @Roles(...) check — codified once in the global RolesGuard. We never need to add SUPER_ADMIN to a per-controller list.

Location scoping (admins)

  • List endpoints filter by locationId IN admin.locations (directly or via the relevant FK chain — e.g. fees scope through fee.class.locations).
  • Write endpoints check that any locationIds the request would attach are a subset of the admin's allowed set. Trying to create a class at a location you can't access → 403.

User-management policies

  • SUPER_ADMIN can create any role; creating SUPER_ADMIN requires no tenantId.
  • ADMIN cannot create SUPER_ADMIN or another ADMIN — 403.
  • ADMIN cannot delete a SUPER_ADMIN — 403.
  • SUPER_ADMIN cannot delete themselves — 403.
  • Self-edit of name / password / language is always allowed.

Password reset

  • POST /auth/forgot-password always returns 200 with the same generic message — does not disclose whether the email is registered.
  • Reset tokens are SHA-256 hashed at rest; raw token only ever exists in the email URL. TTL is 1 hour by default (PASSWORD_RESET_TTL_HOURS).
  • Only the latest unused token works — issuing a new request marks any prior tokens used.
  • Successful reset revokes every active refresh token for that user — all sessions die.
  • No auto-login on reset — the user is bounced to /login to authenticate with the new password.
  • Inactive accounts are silently skipped — reset is not a re-activation channel.

20 Troubleshooting

"Invalid credentials" at login

  • Double-check the email and password. A wrong email or password returns this exact error to avoid leaking which accounts exist.
  • Confirm the user is active. Deactivated users cannot log in.
  • Confirm the account's tenant is active — a user whose tenant has been deactivated cannot log in.
  • Forgot the password entirely? Use Forgot your password? on the login page.

I never received the password-reset email

  • Check your spam folder.
  • The form always shows the same generic message either way — so an unknown address looks identical to a real one that ran into a delivery issue. Confirm the email is the one tied to your account.
  • In dev (MAIL_TRANSPORT=console) the email is printed to the backend log, not actually sent. Look for a "OUTGOING MAIL" block in the dev-server output.
  • Inactive accounts don't receive reset emails. Ask an admin to re-activate yours first.
  • The reset link is valid for 1 hour. After that, request a new one.

The reset link says "invalid or expired"

  • The link expired (1-hour window).
  • The link was already used.
  • You requested a newer reset for the same account — only the latest link works.
  • The account was deactivated after the link was issued.
  • Solution: open /forgot-password and request a fresh one.

"X-Tenant-Id header required for SUPER_ADMIN"

You're logged in as a super admin but no tenant is selected. Open the tenant selector in the navbar and pick one.

"Forbidden" when creating something at a location

You're an admin trying to attach a resource to a location outside your assigned set. Either ask a super admin to widen your assignment, or pick a location you actually own.

"At least one contact is required for trainees under 18"

The DOB you entered makes the trainee a minor. Add at least one guardian contact in the Guardian contacts section before submitting.

"A class with this name already exists"

Class names must be unique within a tenant. Pick a different name.

Generated 0 sessions / 0 fees

  • For sessions: do you have any active schedules in the date range?
  • For fees: do you have PER_MONTH (or PER_SESSION) classes with at least one trainee linked at a location both share?
  • Re-running the generator on the same range is always a no-op for already-existing rows.

Customer can't see their fees

  • The customer account must be linked to one or more trainees in the tenant.
  • The trainee must have at least one fee. If the admin hasn't generated this month yet, the portal will be empty.
